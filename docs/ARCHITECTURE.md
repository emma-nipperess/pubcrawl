# Architecture

## Overview

```
Browser (React SPA on GitHub Pages)
  ├─ supabase-js ── PostgREST ── Postgres (RLS on every table, SECURITY DEFINER RPCs)
  ├─ supabase-js ── Auth (anonymous guests, optional email OTP)
  ├─ XHR / supabase-js ── Storage (private `proof`, public `event-assets`)
  └─ supabase-js ── Realtime (Postgres Changes, RLS-filtered) → cache invalidation
```

Stack: Vite 6, React 18, TypeScript (strict), React Router 6, TanStack Query 5, supabase-js 2, lucide icons, self-hosted Fontsource fonts, `qrcode`. No CSS framework — a small token-based design system in `src/styles/`.

## Data model

Relational, event-scoped. Key tables: `events`, `event_invites` (code, separate so it's never exposed to participants), `event_members` (role, status, late-join position), `venues`, `venue_organiser_notes` (organiser-only), `teams`, `team_members` (history: `joined_at`/`left_at`, one current row per member), `challenges`, `challenge_answers` (organiser-only answer keys), `challenge_submissions`, `submission_media`, `venue_participation`, `score_ledger`, `score_adjustments`, `event_announcements`, `achievement_definitions`, `member_achievements`, `event_templates`, `event_audit_log`.

## Security model

- Clients get **no INSERT/UPDATE grants** on anything that affects game state. Column-level grants allow only safe fields (e.g. a participant can change their display name/avatar, not `role` or `status`).
- Every sensitive operation is a `SECURITY DEFINER` function with `search_path = ''`, which checks `auth.uid()` itself: `create_event`, `join_event`, `set_event_status`, `advance_venue`, `submit_challenge`, `review_submission`, `adjust_score`, `apply_team_plan`, `skip_venue`, etc.
- RLS helpers live in a non-exposed `private` schema.
- An invite code only lets someone call `join_event` as a participant. Roles can only be changed by the event owner (`set_member_role`), never by the member themselves.
- Organisers can't approve their own submissions (unless they are the owner, who has no one else to defer to). Co-organisers can't remove other co-organisers.
- Private events are only reachable by invite code; `get_event_preview` by id works only for public events or existing members. Draft events aren't previewable by code except by the owner.
- Challenges are hidden by RLS until their venue opens (or the configured reveal time) — the browser never receives unrevealed challenge text.

## Scoring

All points live in `score_ledger`, written only by trusted functions. Each row has a deterministic `ledger_key` (`sub:<id>:points`, `vb:<venue>:<member>`, `skip:<participation>`, `adj:<adjustment>`) under a unique constraint, so a retry, refresh or re-sync can never double-award.

- **Submission ids are generated by the client** and reused on retry; `submit_challenge` returns the original row if the id exists. A partial unique index on `dedupe_key` (`m:<member>:<challenge>` or `t:<team>:<challenge>`) for live (pending/approved) submissions plus a per-key advisory lock stop concurrent duplicates.
- Points are **snapshotted** on the submission when it is made. Editing a challenge's points later affects only future completions; past awards are never silently recalculated. Type and individual/team scope are locked once submissions exist.
- `pending` earns nothing unless the event enables provisional scoring, in which case ledger rows are flagged `provisional` and shown separately.
- Rejection applies the challenge's penalty (if any). Overturning a decision re-syncs that submission's rows.
- Venue clean-sweep bonuses are recalculated idempotently after each submission change.
- Organiser corrections insert a `score_adjustments` row (original, new, delta, reason, actor, timestamp) and a matching ledger row.

### Team challenges and team changes

- A team challenge credits the **team once** (ledger row with `team_id`, `member_id = null`). With `team_and_members`, each member who was on the team at submission time additionally gets an individual row with `team_id = null` — so the team total is never multiplied by head-count.
- Individual submissions record the member's team at submission time (`team_id`). That team keeps those points forever.
- **Moving teams**: the member's history row is closed and a new one opened. Points already earned stay with the old team; the member's personal total is unchanged; the new team gains only what is earned after the move. Non-repeatable individual challenges can't be re-earned (dedupe is per member), and team challenges the new team already completed can't be repeated.
- Leaving or being removed hides a person from the individual board; points they earned for their team remain.

### Leaderboard and ties

`get_leaderboard` computes ranks in SQL with standard competition ranking (1, 1, 3). Tie-break options: `shared` (equal rank), `most_completed` (more completed submissions first), `earliest` (whoever reached their score first). Anything still equal shares a rank and is flagged `tied`. Hidden leaderboards show only your own/team rows until the event is completed.

## Event lifecycle

`draft → published → in_progress ⇄ paused → completed → archived`, plus `cancelled` from any pre-completion state. Enforced by `public.event_status_transition_allowed` in the database; the UI mirrors it in `src/features/events/status.ts`. A published event with participants can't return to draft. Starting opens the first venue; advancing closes the current one and marks any jumped-over upcoming venues as skipped.

## Late joining and skipping

- `join_event` records `joined_late` and the venue position at join time. Earlier venues show as "before you joined" — not missed, not penalised.
- `skip_venue` records a `skipped` participation (with optional reason). It never creates submissions or awards points; it blocks submissions for that venue until `resume_venue` (allowed while the venue is still upcoming/active).
- Skip policy: `none` (no penalty), `zero` (shown as missed/zero), `penalty` (idempotent negative ledger row). Organiser overrides (`override_participation`) waive penalties.

## Media

1. The picker reads the first bytes of the file to detect its real type (magic numbers), checks size, downscales photos to 2048 px (re-encoding strips EXIF/GPS) and makes a 480 px thumbnail / video poster frame on-device. Undecodable formats (e.g. HEIC outside Safari) upload unchanged.
2. Files upload with progress via XHR to `proof/{event}/{uid}/{submission}/…` with `x-upsert: false`. Storage itself enforces the bucket's size and MIME allow-list. Policies require the uploader's own folder, active membership, a live event, and that the submission doesn't exist yet (folders are sealed once a submission is recorded).
3. `submit_challenge` verifies each path is in the caller's folder for that submission, exists in `storage.objects` owned by the caller, and uses **Storage's recorded MIME type** (not the client's claim) to validate photo vs video.
4. Viewing uses 30-minute signed URLs, requested lazily when tiles scroll into view; full-size files load only on tap.
5. Abandoned uploads are deleted when a participant discards an attempt or a submission is definitively refused. Organisers can delete individual media or purge an event's media (Settings → Data).

Limitation: the browser can't fully verify content (e.g. a polyglot file). Storage serves objects with their stored content type and signed URLs, and media is only ever rendered via `<img>`/`<video>`.

## Realtime

One channel per open event subscribes to Postgres Changes on the event's tables (filtered by `event_id`; RLS applies server-side). Changes are treated as signals: affected TanStack Query caches are invalidated (debounced 350 ms) and refetched from the authoritative tables/RPCs. On reconnect, `online`, or tab visibility, everything is refetched; while disconnected the app polls every 20 s and shows a reconnecting/offline banner. Channels are removed on unmount.

## Templates & themes

Theme metadata (`src/features/themes/themes.ts`) + CSS palettes/typography (`src/styles/themes.css`) + SVG motifs (`ThemeScope.tsx`). Starter content per theme lives in `src/features/templates/content.ts`. To add a theme: add an entry to `THEMES`, a `[data-theme='x']` block, a motif, and a `TEMPLATES` entry — no other code changes. Organiser templates are stored as JSON payloads in `event_templates` (private to the owner); `duplicate_event` copies configuration, venues and challenges but no people, submissions, scores or media.

To add a challenge type: extend the CHECK constraint in a new migration, add it to `CHALLENGE_TYPES` (`src/features/challenges/meta.ts`), and handle any special input in `SubmitSheet`.

## Offline / PWA

`public/sw.js` caches only hashed static assets (JS/CSS/fonts/icons). It never caches HTML, API, Auth, Storage or Realtime traffic, so private data isn't stored offline on shared devices. In-progress form data (wizard, join form, challenge answers) is kept in local/session storage until submitted.
